# Продуктовые метрики

Из `backend/` в окружении с `DATABASE_URL` той же БД, что у API:

```sh
python -m app.scripts.product_metrics
python -m app.scripts.product_metrics --dvizh-id <id>
```

Команда только читает БД. Без фильтра выдаёт последние 20 движей в JSON. В отчёте
есть ID движа, отметки времени событий и агрегаты; нет имён, MAX ID, реакций отдельных
людей, токенов или webhook secret. Публичного analytics endpoint и внешнего трекера нет.

| Событие | Источник |
| --- | --- |
| `signal_created` | `Intent.created_at` сигнала конкретной компании |
| `dvizh_launched` | `DvizhSession.launched_at`, записывается при первом успешном запуске |
| `review_notification_sent` | Самый ранний `sent_at` успешно отправленного `DVIZH_REVIEW_REQUIRED` |
| `first_reaction` | Первая сохранённая реакция участника, кроме инициатора; учитывает и пропуск |
| `match_found` | Создание первого outbox `DVIZH_MATCH_FOUND`, независимо от доставки |
| `final_confirmation` | Самый ранний `confirmed_at`, установленный при успешном подтверждении |
| `dvizh_gathered` | Создание первого outbox `DVIZH_GATHERED`, независимо от доставки |

Время от запуска до реакции, match и gathered выводится в секундах. Это первые
события за жизнь движа, даже если позже вариант был заменён или источник отменён.
`number_of_review_notifications` считает только `SENT`, исключая pending/failed и
уведомления автору до запуска. `SENT` означает успешный ответ MAX API, а не прочтение.
`number_of_confirmations` — число текущих `CONFIRMED` у активного варианта;
waitlist, отказы и подтверждения заменённых вариантов не считаются.

Миграция `20260927_0013` добавляет только `launched_at`, `sent_at`, `confirmed_at`
в существующие таблицы. Старые значения остаются NULL: время создания движа не
выдаётся за время запуска, время создания outbox — за доставку, а время отказа —
за подтверждение. Неизвестное время и отрицательная длительность выводятся как
`n/a`; известные счётчики старых записей остаются доступны. Для новых реакций и
outbox время создания берётся в момент действия; часы backend-процессов должны
быть синхронизированы. Удаление исходных записей уменьшает доступную историю.

`manual_messages_by_initiator_after_launch = 0` помечено как **свойство сценария**:
приложение само создаёт уведомления после запуска. Это не измерение переписки;
сообщения пользователя вне сценария не отслеживаются.
