# Проверки

## Автоматические проверки

Нужны Node.js 24, npm и Docker Compose v2. Backend-проверки ниже используют Python и зависимости из Docker-образа, отдельная локальная установка Python не нужна.

```powershell
npm --prefix frontend ci
npm --prefix frontend run check
docker compose build
docker compose up -d --no-build
```

`npm run check` выполняет Prettier, ESLint, TypeScript, Vitest и production build. Frontend-тесты используют mock API и не являются браузерным E2E. Backend покрывает домен, API, приватность, нормализацию провайдера, кеш и outbox; тесты конкурентности требуют настоящую PostgreSQL.

Один раз создайте отдельную тестовую БД; если она уже существует, пропустите создание:

```powershell
docker compose exec -T postgres psql -U max_dvizh -d postgres -c "CREATE DATABASE max_dvizh_test OWNER max_dvizh;"
```

Затем:

```powershell
docker compose run --rm --no-deps backend ruff check .
docker compose run --rm --no-deps backend ruff format --check .
docker compose run --rm --no-deps backend mypy app scripts
docker compose run --rm --no-deps -e TEST_DATABASE_URL=postgresql+psycopg://max_dvizh:local_development_only@postgres:5432/max_dvizh_test backend pytest
```

Тесты пересоздают таблицы в `TEST_DATABASE_URL`. Никогда не указывайте рабочую БД. При изменённых `POSTGRES_*` замените локальные реквизиты в командах. Без `TEST_DATABASE_URL` pytest намеренно завершается ошибкой, а не пропускает PostgreSQL-тесты.

CI в [.github/workflows/check.yml](../.github/workflows/check.yml) выполняет эти проверки, а также чистую миграцию до `20260918_0010` и обновление заполненной `20260916_0005` с проверкой сохранности данных. Эти проверки используют отдельные CI-базы. Перед сдачей дополнительно проверьте зависимости (`npm --prefix frontend audit`), лицензии и отсутствие рабочих секретов.

## Compose smoke и OpenAPI

После `docker compose up -d --no-build` дождитесь готовности:

```powershell
docker compose ps
Invoke-RestMethod http://localhost:8000/api/v1/health/ready
(Invoke-WebRequest http://localhost:8080/).StatusCode
./scripts/export-openapi.ps1
git diff --exit-code -- docs/openapi.json
```

Ожидаются готовые PostgreSQL/backend/Redis, работающие frontend/worker/scheduler, успешный readiness и HTTP 200 страницы. При задержке повторите запросы; при ошибке смотрите `docker compose logs --tail=80`. API на `http://localhost:8000/openapi.json` должен совпадать с экспортом, а методы и пути [DATA-API.yaml](../DATA-API.yaml) — присутствовать в контракте. Изменение OpenAPI при cleanup недопустимо.

Остановка без удаления данных — `docker compose down`. Для чистого воспроизведения используйте отдельный clone/Compose project. `down -v` удаляет его локальные данные. Измеряйте сборку отдельно от первичной загрузки базовых образов; лимит кейса — пять минут.

## Критерии приёмки

| Область | Что проверить |
| --- | --- |
| Приватность и вход | Чужие условия, координаты, бюджет, причина Near, отказ и очередь недоступны; неверная/старая подпись MAX и доступ к чужим объектам отклоняются. Одновременные первые запросы создают одного пользователя. |
| Бюджет и расстояние | 500→400 Exact; 300→400 Near в пределах допуска, только с явным согласием; превышение допуска Conflict. Неизвестная цена с бюджетом и координаты без возможности проверить радиус — Unverified. Без соответствующего условия отсутствие факта не блокирует. Только собственные километры, не минуты. |
| Создание плана | Только Conflict/Unverified не создают план и снимок. Одного Exact/Near достаточно для начала сбора; недостаточно для подтверждения. |
| Размер и очередь | Минимум и максимум каждого принятого соблюдены. Все 7 совместимых получают приглашения на «ровно 5»; первые 5 занимают места, остальные приватно ждут. Отмена продвигает первого подходящего. Полный обычный диапазон не предлагает очередь. |
| Подтверждённое ядро | Двое с min=2 остаются подтверждёнными после ответа человека с min=5. Он ждёт лично, затем присоединяется при допустимом составе; отмена сохраняет оставшееся допустимое ядро. |
| Полный пул и пересечения | Пять приглашений из разных компаний, включая Near, доступны одновременно. Выбор не автоматический; пересекающиеся варианты пересчитываются, независимые сохраняются. Повторный пересчёт не возвращает отказавшегося. |
| Конкурентность | Параллельные ответы не превышают вместимость и не принимают пересекающиеся приглашения одного пользователя. Параллельная генерация не дублирует план, Offer и outbox. |
| Время | Полный Event помещается в доступность, его конец не удлиняется. Автосигнал учитывает IANA timezone, день недели, ночное окно, паузу; scheduler не обрабатывает одну задачу параллельно и учитывает время вычисления. |
| Сигналы и точки | Пакет создаётся/редактируется/отменяется атомарно, смешанные города отклоняются. Ошибка пересчёта откатывает пакет; refresh идемпотентен. Точки свои и того же города, rename/default/delete соблюдают ограничения использования. |
| Провайдер | Отдельные сеансы Events, места со слотами и предупреждением о часах, «от» как нижняя граница. Лучший допустимый слот на место/день; при равенстве ранний. Обычный салон не попадает в «Бани и спа». |
| Кеш и ошибки | Ключи разделяют город/окно/категории; hit не вызывает KudaGo; пригодный кеш переживает сбой источника. Снимок плана доступен после вытеснения кеша. Нет скрытого каталога PostgreSQL и подмены моделью. |
| Истечение и восстановление | Просроченное приглашение нельзя принять; до закрытия приёма возможна отмена. Проверяются динамический TTL приглашения и закрытие за 10 минут до начала. Нет источников, нет совместимости и сбой провайдера различаются; есть повторный поиск. Неизвестная ссылка — 404, явно истёкшая — 410. |
| MAX и сдача | Реальный сценарий, уведомление и share работают в mobile/web; Docker воспроизводим, OpenAPI согласован, модельные данные помечены. |

## Ручная проверка в браузере

В репозитории нет автоматизированного браузерного E2E runner. Проверяйте production frontend из Compose на 375×812, 430×932 и 1280×800, в светлой и тёмной теме, с клавиатурой и длинным русским текстом.

1. Откройте `http://localhost:8080`, создайте явно названную демонстрационную Компанию. Скопируйте ссылку из «Компания». Через «Локальная проверка» переключитесь на второго демонстрационного пользователя и войдите по ссылке. Проверьте повторный вход, неизвестную и истёкшую ссылку.
2. Создайте Сигнал с временем и категориями, затем измените и отмените его. Повторите для двух компаний одного города. Без сохранённой точки расстояние не предлагается; с реальной GPS-точкой проверьте имя, default, город и отказ удаления используемой точки.
3. Для подходящих Сигналов дождитесь реальных результатов KudaGo. Если нужны фиксированные сценарии, отдельно вызовите `POST /api/v1/development/seed-demo/{group_id}` от участника в development. Модельная отметка обязательна; такой сценарий не считается проверкой провайдера.
4. Проверьте полный пул приглашений, Exact и бюджет Near. Near без явного подтверждения не добавляет участника. Выберите пересекающийся вариант и убедитесь, что независимое приглашение остаётся.
5. Соберите минимум: «Собираем» меняется на подтверждённый план, остаются свободные места. Проверьте более строгий личный минимум, точную очередь, отмену и продвижение; имена появляются только у подтверждённого состава. Отдельно проверьте 8 приглашённых с минимумом 3.
6. Создайте, измените, приостановите и возобновите Автосигнал. Проверьте ночное окно и появление приглашения от scheduler без открытого приложения.
7. Проверьте отсутствие Сигнала/мест/планов, пустой источник, отсутствие подходящих вариантов, загрузку и ошибку. После успешной выборки сделайте KudaGo недоступным в тестовом окружении: действующий кеш допускается, без него нужен понятный отказ и повторный поиск.
8. Проверьте карточки бесплатного события, цены «от», места с адресом и непроверенными часами; личные данные не должны появляться у другого пользователя. Диалоги сохраняют и возвращают фокус, нет горизонтального переполнения и ошибок консоли. Повторите основной путь без сброса базы.

## Реальный MAX после deployment

Обязательная отдельная ручная проверка в MAX mobile и MAX web:

1. Войти через зарегистрированного бота в Mini App с настоящей подписанной личностью.
2. Создать/выбрать Компанию, присоединиться вторым аккаунтом через `startapp`; отдельно проверить разрешённую привязку чата.
3. Подать Сигнал или активировать Автосигнал, получить личное приглашение и открыть его из уведомления бота.
4. Подтвердить Exact/Near явным действием, собрать допустимый состав, получить уведомление о плане и открыть ссылку на него.
5. Отправить план через MAX share, вернуться в приложение, проверить восстановление после ошибки и повторное прохождение.

Фиксируйте дату, версию клиента, commit и результат каждого шага. Browser/mock-тесты не подтверждают прохождение этой проверки. На типичных компаниях 4–12 человек также измерьте время генерации с репрезентативной выборкой провайдера; не заявляйте производительность без замера.
