# ДВИЖ — реализованное направление

## Визуальная система

Мобильный интерфейс реализован по концептам в `docs/redesign-concepts/`. Ориентир для приглашения — `invitation-social-max.png`. Приглашение и готовый план используют один компонент `EventCard`: афиша, факты, компания и действия имеют общие боковые поля и одинаковый ритм. Форму и поиск сверяли с `signal-form-max.png` и `search-waiting-max.png`. Концепты содержат примерные данные; рабочие время, адрес, цена, компания и прогресс берутся из backend. Кассета удалена; в афише используется лёгкая геометрия без отдельной картинки на каждую тему.

По уточнению заказчика прежняя жёлтая палитра заменена цветами MAX: основной синий `#471AFF`, пурпурный `#9500FF`, фиолетовый `#6E1AFF`, голубой `#00BFFF`, белый `#FFFFFF`, тёмный `#0D001A`. Светлые поверхности и границы выведены из них для длинных форм и карточек. Шрифт Max Sans загружен локально в Regular и Medium из [официального набора MAX](https://business.max.ru/static/docs/MAX_b2b_toolkit.pdf). Обычные подписи и строки используют Regular; Medium оставлен для крупных заголовков и основных действий. Цвета сверены с [брендбуком MAX](https://go.max.ru/brandbook). Основные кнопки имеют высоту 54–58 px, карточки — радиус 18–24 px; интерфейс ограничен колонкой 480 px.

## Сценарий

- Три раздела: Главная, Планы, Компания. Регулярный поиск создаётся переключателем в общей форме.
- Главная всегда начинается с названия «ДВИЖ» и одной и той же большой карточки «Когда двигаемся?» с кнопкой «Подать сигнал» и настройкой повтора. Сигналы и приглашения идут ниже карточки. В пустом состоянии под ней есть компактная карточка компании с реальным названием, числом участников и переходом в раздел. Готовые и собирающиеся планы находятся только во вкладке «Планы».
- Нижняя навигация использует согласованные контурные и заполненные фиолетовые иконки для всех трёх разделов. Во вкладке «Планы» заголовки групп появляются только тогда, когда одновременно есть готовые и собирающиеся планы.
- Форма содержит пресеты с точным интервалом времени, быстрый выбор «Любой вариант» и поиск по 12 доступным направлениям, компанию, необязательные ограничения, еженедельное повторение и локальный черновик. Место добавляется с геолокацией. Подробные направления (квесты, театр, музеи и другие) поддерживаются фильтрами backend.
- Экран компании показывает сначала выбор компании, затем её участников через `GET /groups/{group_id}/members`. Переключение компании остаётся в этом разделе и обновляет участников. Список доступен только членам компании. Город выбирается в собственном компоненте, добавление места раскрывается внутри раздела.
- Повторяющийся сигнал на паузе показывает «Возобновить» и запускает `POST /autosignals/{id}/resume`; действие «Остановить» доступно только активному сигналу. В подтверждении остановки кнопка возврата называется «Назад».
- Индикатор поиска анимируется только CSS-преобразованием, без новых сетевых запросов; при `prefers-reduced-motion` движение отключено.
- `NEAR` требует отдельного согласия перед запросом принятия. `UNVERIFIED` не выводится как принимаемое приглашение.
- Переход на MAX по `startapp=offer_<id>` и `startapp=plan_<id>` сохранён.

## Возможности, требующие изменения API

- `GET /plans` возвращает только предстоящие планы. Для вкладки «Прошедшие» нужен доступ к истории.
- Нет endpoint выхода из компании. Кнопка не добавлена.
- Места сохраняются по координатам. Поиск адреса требует согласованного источника геокодинга или поддержки backend.
- Создание разового сигнала синхронно запускает поиск. Для быстрого отдельного состояния поиска нужен асинхронный endpoint или фоновая задача. Пока запрос выполняется, показывается содержательный экран ожидания и обрабатывается timeout.
- Переключение разового и регулярного сигналов сейчас выполняется двумя запросами с откатом при ошибке. Для гарантированно атомарного переключения нужен backend endpoint конвертации.
- Для надёжного повтора после timeout нужен idempotency key на создание. Сейчас frontend сначала проверяет сохранённые сигналы и не повторяет запрос автоматически.
- Для отдельного объяснения `UNVERIFIED` backend должен возвращать безопасную причину, почему обязательное условие невозможно проверить.

## Проверка

`npm run check`: форматирование, lint, typecheck, 61 тест и production build проходят. Для изменённого адаптера каталога проходят Ruff и 11 тестов нормализации и кеша. Полный backend-набор в этой среде нельзя запустить на установленном Python 3.14 из-за несовместимости установленного SQLAlchemy при сборе тестов; backend рассчитан на Python 3.13.

Браузерный проход в локальном Chromium с моками API: 34 состояния на ширинах 320, 360, 390, 430 и 1280 px; главный экран с пустым и заполненным состоянием, пауза и возобновление поиска, форма, полный каталог и поиск по нему, раскрытые условия, добавление места и меню его действий, поиск, приглашение, согласие `NEAR`, подтверждённый план, разделы «Планы» и «Компания» с переключением компании, создание компании, города, длинное название компании, отсутствие источников и совпадений, недоступность провайдера. Проверка ждёт загрузки Max Sans перед снимком. Горизонтальной прокрутки и ошибок консоли нет. Проверено отключение анимации при уменьшении движения. Актуальные снимки — в `docs/redesign-qa/`; подробности — в `design-qa.md`.
