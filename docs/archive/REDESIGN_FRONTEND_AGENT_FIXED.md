# MAX ДВИЖ — задание агенту на полный UX/UI-редизайн фронтенда

## Роль и цель

Ты работаешь как senior product designer и senior frontend engineer. Нужно не слегка «освежить стили», а переработать пользовательский опыт MAX Mini App **ДВИЖ**, сохранив существующую бизнес-логику и интеграцию с backend.

Главная цель:

> Приложением должно быть можно пользоваться почти без чтения и размышлений: крупные элементы, короткие тексты, одно очевидное главное действие, понятное состояние после каждого нажатия.

Если пользователь вынужден разбираться, что такое сигнал, автосигнал, matching или почему ничего не произошло, интерфейс не выполнен.

## Контекст продукта

ДВИЖ помогает компании друзей договориться о досуге:

1. Каждый сообщает, когда и куда готов пойти.
2. Система ищет события и места, совместимые с условиями участников.
3. Каждый получает личное приглашение на подходящий вариант.
4. Когда набралось нужное количество участников, появляется подтверждённый план.

Основная формула продукта:

> **ДВИЖ не мэтчит людей. ДВИЖ собирает выполнимый план.**

Frontend: React 19, TypeScript, Vite, MAX UI, nginx.

Рабочее приложение: `https://dvizhfrontend.relaxdev.ru`

Backend: `https://max-dvizh.relaxdev.ru`

Репозиторий: `https://github.com/lekovvv-cmd/max-dvizh`

Перед работой изучи актуальный репозиторий, существующие маршруты, типы, API-клиент и состояния. Не выдумывай новые backend-контракты, пока не проверишь существующие. Если для идеального UX backend-возможности не хватает:
- не маскируй отсутствие возможности фейковым UI;
- реализуй только безопасный frontend fallback, если он действительно возможен;
- отдельно перечисли необходимое изменение API;
- не подключай новые внешние сервисы без отдельного согласования.

## Обязательные принципы интерфейса

1. **Mobile first.** Основной сценарий — MAX Mini App на телефоне.
2. **Одно главное действие на экран.** Primary-кнопка должна быть очевидна без чтения инструкции.
3. **Крупные элементы.** Высота основных кнопок 52–56 px, минимальная зона нажатия 44×44 px.
4. **Короткие тексты.** Заголовок до 5–6 слов, пояснение максимум две короткие строки.
5. **Не показывать внутренние термины.** Никаких `matching`, `CandidatePlan`, `EXACT`, `NEAR`, `UNVERIFIED`, `worker`, `scheduler`, `ekb` и подобных сущностей.
6. **Прогрессивное раскрытие.** Сначала время, интересы и компания. Бюджет, расстояние и количество людей — в блоке «Дополнительные условия».
7. **Не использовать пустые экраны как тупики.** Каждый empty state объясняет ситуацию и содержит следующее действие.
8. **Не терять ввод.** Черновик формы сохраняется при переходе, возврате и временном закрытии Mini App.
9. **Никаких голых спиннеров.** Всегда показывать, что именно происходит и можно ли закрыть приложение.
10. **Русский формат.** Даты, время, города и числа должны отображаться по-русски.
11. **Доступность.** Все интерактивные элементы — семантические кнопки/поля с доступными именами, видимым фокусом и достаточным контрастом.
12. **Не перегружать декоративностью.** Визуальный стиль энергичный и дружелюбный, но главнее скорость понимания.
13. **Никаких фейковых функций.** Не показывать маршрут, календарь, адресный поиск, бронирование или другие возможности, если текущий frontend/backend реально их не поддерживает.

## Итоговая информационная архитектура

Оставить три пункта нижней навигации:

- **Главная** — текущий поиск, ожидание друзей и новые приглашения.
- **Планы** — предстоящие и прошедшие подтверждённые планы.
- **Компания** — участники, приглашение друзей, город и личные места.

Отдельную вкладку **«Авто» удалить**. Автосигнал представить пользователю как опцию **«Повторять каждую неделю»** внутри формы обычного сигнала.

На уровне API продолжать использовать текущую сущность autosignal. Не создавать одновременно обычный Signal и AutoSignal, если текущий API этого не предполагает. При включённом повторении форма должна сохранять регулярный сигнал; при выключенном — обычный разовый. При редактировании сохранять исходный тип сущности, пока пользователь явно его не изменил.

Во время создания и редактирования сигнала нижнюю навигацию скрывать. Использовать верхнюю кнопку «Назад». При попытке выйти с изменениями показывать подтверждение «Выйти без сохранения?».

## Терминология

В интерфейсе использовать:

- «Подать сигнал» — фирменное название основного действия.
- «Ищем вариант» — процесс поиска.
- «Приглашение» — конкретный найденный вариант.
- «План» — подтверждённый вариант с нужным количеством участников.
- «Повторять каждую неделю» — пользовательское название автосигнала.

Слово «сигнал» при первом появлении обязательно объяснить одной строкой. Не заставлять пользователя учить термин до начала работы.

## Экран 1. Главная без активного сигнала

Основной блок:

**Заголовок:** `Когда двигаемся?`

**Текст:** `Отметь, когда и куда ты готов пойти. Друзья сделают то же самое — ДВИЖ найдёт общий вариант.`

**Primary CTA:** `Подать сигнал`

Ниже показать короткую визуальную механику без длинного текста:

`Выбрали условия → получили приглашение → план собран`

Вторичный компактный блок:

**Заголовок:** `Собираетесь регулярно?`

**Текст:** `Настрой повторение, например каждую пятницу.`

**Action:** `Настроить`

Нельзя использовать текущую формулировку «Сигнала пока нет» как главный смысл экрана.

## Экран 2. Создание сигнала

Это один вертикальный экран с крупными секциями. Не делать длинный пошаговый wizard, если он увеличивает количество нажатий.

### Заголовок

`Когда двигаемся?`

### Секция «Когда»

Крупные selectable chips/cards:

- `Сегодня после 20:00`
- `Завтра вечером`
- `На выходных`
- `Выбрать время`

Не показывать прошедший вариант disabled. Если «Сегодня вечером» уже недоступно, убрать его полностью.

При ручном выборе показывать русские поля:

- `21 сентября, 20:00`
- `21 сентября, 23:00`

Проверять:

- начало не в прошлом;
- окончание позже начала;
- понятная inline-ошибка непосредственно возле поля.

### Секция «Что подходит»

Подсказка: `Можно выбрать несколько.`

Варианты:

- `Всё равно`
- `Игры`
- `Активный отдых`
- `Культура`
- `Концерты`
- `Бани и спа`

«Всё равно» взаимоисключающее: при выборе конкретной категории оно снимается; при выборе «Всё равно» снимаются категории.

### Секция «С кем»

Показывать большую карточку компании:

**Друзьяки**  
`Антон и ещё 3 человека`

Выбранное состояние должно быть визуально очевидно. Если компания одна, выбрать автоматически. Не показывать `1 человек · ekb`.

### Секция «Дополнительные условия»

По умолчанию свёрнута.

**Заголовок:** `Бюджет, расстояние и компания`

**Подпись:** `Необязательно`

После раскрытия:

#### Бюджет

- Неважно
- До 500 ₽
- До 1 000 ₽
- До 2 000 ₽
- Своя сумма

#### Расстояние

Сначала выбрать точку:

- Дом
- Работа
- Текущее местоположение
- Добавить место

После выбора точки:

- До 2 км
- До 5 км
- До 10 км
- Неважно

Поле радиуса не может быть активно без выбранной точки.

#### Количество участников

- Неважно
- Хотя бы 3
- Хотя бы 5
- Ровно…

Пояснение: `Сигнал сработает, когда наберётся указанное количество участников.`

### Повторение

Переключатель:

`Повторять каждую неделю`

После включения показать дни недели и интервал времени. Это создаёт/редактирует существующий autosignal через текущий API.

Важно:
- не создавать одновременно обычный Signal и AutoSignal, если backend-модель предполагает один из двух вариантов;
- при включённом повторении сохранять регулярный сигнал;
- при выключенном — разовый;
- редактирование существующего регулярного сигнала должно оставаться регулярным, если пользователь явно не выключил повторение.

### Sticky footer

Над кнопкой показать резюме выбора, например:

`Сегодня после 20:00 · Всё равно · Друзьяки`

Кнопка:

`Начать поиск`

При отправке текст меняется на `Сохраняем…`. Запретить повторное нажатие и создание дублей.

## Добавление места

Нажатие `Добавить место` не должно уводить в раздел «Компания» и уничтожать контекст формы.

Открывать bottom sheet/modal поверх текущей формы:

**Заголовок:** `Новое место`

Использовать только реально поддерживаемые текущим проектом возможности.

Минимальный безопасный вариант:

- Название, default `Дом`
- `Использовать мою геопозицию`
- превью полученной точки/подписи адреса, если это уже поддерживается
- `Сохранить место`

После сохранения закрыть modal, вернуться в исходную форму и автоматически выбрать новое место. Все данные формы должны сохраниться.

При отказе в геолокации показать: `Не получилось определить геопозицию.`

### Важно про адресный поиск

Не подключать новый геокодинг-сервис самостоятельно.

Если текущий backend умеет сохранять только координаты:
- не рисовать неработающее поле `Адрес`;
- оставить рабочую геолокацию;
- отдельно зафиксировать API-gap для полноценного адресного поиска.

Если в проекте уже есть допустимый и реально работающий источник геокодинга — использовать его только после проверки текущего контракта и лицензии.

## Экран 3. Поиск после подачи сигнала

Не держать пользователя 10–15 секунд на форме с голым спиннером.

После успешного сохранения сигнала сразу открыть главную и показать статус:

**Заголовок:** `Ищем подходящий план`

**Текст:** `Проверяем события, места и условия друзей.`

Этапы:

- `Сигнал сохранён` — completed;
- `Ищем варианты` — active;
- `Проверяем компанию` — pending.

Подпись: `Можно закрыть приложение — мы пришлём приглашение в MAX.`

Действия:

- `Изменить условия`
- `Остановить поиск`

Предпочтительная архитектура: создать сигнал быстрым запросом, затем обновлять статус асинхронно/polling.

Если backend сейчас выполняет matching синхронно:
- не менять backend молча;
- сразу показать отдельный полноценный loading screen с указанными текстами;
- обработать timeout/retry;
- не имитировать асинхронное состояние, которого нет.

## Экран 4. Результаты поиска

Нельзя использовать одно универсальное сообщение «События и места есть, но условия пока не совпали». Реализовать отдельные состояния.

### Состояние A: ждём участников

**Заголовок:** `Ждём ещё одного участника`

**Текст:** `Подходящий вариант есть, но для плана нужно минимум 3 человека.`

Прогресс: `2 из 3 готовы`

CTA: `Позвать друзей`

Не раскрывать чужие бюджеты, координаты, минимумы, причины отказов или несовместимости.

### Состояние B: в каталоге ничего нет

**Заголовок:** `На это время ничего не нашли`

**Текст:** `Попробуй расширить время или выбрать больше категорий.`

Действия:

- `Добавить завтра`
- `Выбрать любые категории`
- `Изменить условия`

### Состояние C: слишком узкие условия

**Заголовок:** `Пока ничего не совпало`

**Текст:** `Можно немного расширить условия. Другие участники не увидят твои ограничения.`

Показывать только безопасные персональные предложения:

- `Увеличить радиус до 10 км`
- `Разрешить варианты на 200 ₽ дороже`
- `Продолжить ждать`

### Состояние D: найден вариант

Большая карточка:

**Есть вариант!**

`Квиз «Музыка 2000-х»`  
`Сегодня, 20:30`  
`Бар «Самоцвет» · 2,4 км`  
`Около 600 ₽ с человека`  
`Подходит 3 участникам`

Primary CTA: `Я пойду`

Secondary:

- `Подробнее`
- `Не подходит`

Для `NEAR` явно показать отклонение и запросить согласие: `На 100 ₽ дороже твоего бюджета.`

### Критично: `UNVERIFIED`

`UNVERIFIED` **не является обычным приглашением и не должен создавать принимаемый Offer**.

Нельзя показывать его рядом с обычными приглашениями с CTA `Я пойду`.

Если backend возвращает состояние, означающее, что обязательное условие невозможно проверить:
- использовать это только для объяснения отсутствия обычного приглашения;
- можно показать нейтральную информационную подсказку, например: `Не можем проверить стоимость этого варианта.`;
- не давать действие, которое обходит обязательное пользовательское условие;
- не превращать `UNVERIFIED` в `NEAR`.

## Экран 5. После принятия приглашения

Сразу подтвердить действие:

**Заголовок:** `Ты в деле`

**Текст:** `Ждём подтверждения остальных.`

Прогресс: `2 из 3 подтвердили`

Не перебрасывать пользователя в пустой раздел «Планы».

## Экран 6. Подтверждённый план

Это кульминация продукта. Сделать экран эмоциональным, крупным и легко сканируемым.

**Hero:** `⚡ ДВИЖ СОБРАЛСЯ`

Далее:

`Квиз «Музыка 2000-х»`  
`Сегодня в 20:30`  
`Бар «Самоцвет»`

Показать аватары и имена подтвердивших участников. Это допустимо только после подтверждения плана.

### Действия

Главным действием сделать то, что реально поддерживается текущими данными.

Если у плана есть валидная внешняя ссылка источника:
- primary: `Открыть подробности`.

Если реально доступны координаты/адрес и можно безопасно сформировать внешнюю ссылку на карты без нового backend-контракта:
- можно добавить `Открыть маршрут`.

Если это не подтверждено текущим кодом — кнопку маршрута не показывать.

`Поделиться в MAX` — оставить, если существующий MAX Bridge реально работает.

`Добавить в календарь`:
- показывать только если реализована реальная генерация календарного события/ICS или поддерживаемое системное действие;
- не оставлять фейковую кнопку;
- если такой функции сейчас нет — не добавлять её в рамках редизайна.

Ниже: адрес, цена, ссылка на источник, важные детали события — только если эти данные реально есть.

## Визуальное направление

Нужен лёгкий, современный, энергичный мобильный интерфейс:

- белый или очень светлый фон;
- фирменный жёлтый как эмоциональный акцент;
- синий использовать для основных действий, если он уже закреплён в MAX UI;
- крупные заголовки 28–32 px;
- основной текст не меньше 16 px;
- скругления 16–20 px;
- карточки с мягкой границей, без тяжёлых теней;
- достаточно воздуха между смысловыми блоками;
- выбранные chips должны отличаться не только тонкой рамкой, но и заливкой/иконкой;
- важные статусы подкреплять короткой иконкой и текстом;
- не использовать мелкие серые подписи как единственный источник важной информации.

Не превращать интерфейс в корпоративную админку. Это приложение про спонтанный досуг друзей.

## Ошибки и надёжность

Обязательно реализовать:

- понятный timeout;
- retry без потери формы;
- offline/error state;
- защиту от двойной отправки;
- локальное сохранение черновика;
- восстановление экрана после возврата из MAX;
- skeleton или содержательный progress вместо пустого экрана;
- toast только для второстепенных подтверждений, важные ошибки показывать в контексте экрана;
- подтверждение перед остановкой/отменой активного сигнала;
- нормальную обработку пустого ответа и 5xx.

Тексты ошибок:

- `Не удалось начать поиск. Попробовать ещё раз?`
- `Связь пропала. Проверяем, сохранился ли сигнал.`
- `Не удалось загрузить варианты.`

Никогда не показывать пользователю сырой текст исключения или HTTP-код.

## Исправить существующие дефекты

- `Друщзяки` → `Друзьяки`.
- `ekb` → `Екатеринбург`.
- американский формат даты → русский.
- `Добавить место` не должно уводить из формы.
- radius должен быть недоступен без точки.
- редактирование должно сохранять семантику исходного выбора времени.
- bottom navigation не должна приводить к потере заполненной формы.
- loading после подачи сигнала должен объяснять процесс.
- результат при широких условиях не должен необъяснимо сообщать о несовпадении.
- все clickable `div/generic` заменить семантическими интерактивными элементами.

## Ограничения бизнес-логики

Соблюдать приватность:

- до подтверждения плана не показывать чужой бюджет;
- не показывать чужие координаты и сохранённые места;
- не показывать причины отказа;
- не показывать персональные минимумы участников;
- не объяснять конфликт через данные другого человека;
- после подтверждения можно показать имена и аватары принявших.

Совместимость:

- `EXACT` — обычное приглашение;
- `NEAR` — явно показать отклонение и получить согласие;
- `CONFLICT` — не показывать как подходящий вариант;
- `UNVERIFIED` — не создавать обычное приглашение и не давать принять как Offer; использовать только как основание для честного состояния «не можем проверить условие», если это состояние доступно frontend.
- Нельзя превращать `UNVERIFIED` в `NEAR`.

Mixed-min логика не должна позволять участнику с минимумом 5 ломать уже готовый план двух участников. Его состояние должно отображаться как ожидание выполнения собственного условия.

## Порядок реализации

1. Изучить актуальный frontend и API-контракты.
2. Составить карту существующих маршрутов, компонентов и состояний.
3. До изменения кода перечислить:
   - какие UX-состояния уже поддерживаются backend;
   - какие можно реализовать только frontend-логикой;
   - какие требуют backend-доработки.
4. Перестроить информационную архитектуру до визуальной полировки.
5. Реализовать новый главный сценарий: главная → сигнал → поиск → приглашение → план.
6. Встроить регулярность в форму сигнала без изменения backend-семантики.
7. Переделать компанию и добавление места.
8. Реализовать все loading/empty/error/waiting states.
9. Сделать визуальную систему и responsive mobile-first layout.
10. Добавить/обновить тесты.
11. Прогнать приложение вручную на узком мобильном viewport и на desktop.

## Технические требования

- Сохранять строгую типизацию TypeScript.
- Не дублировать server state в нескольких несовместимых локальных состояниях.
- Не ломать MAX Bridge, initData, deep links, share и уведомления.
- Сохранять поддержку `startapp=offer_<id>` и `startapp=plan_<id>`.
- Не удалять Docker/Compose и существующий deployment flow.
- Не менять backend API молча.
- Не добавлять новый внешний сервис без явного согласования.
- Не делать frontend fake-state, который выглядит как подтверждённая backend-функция.
- Сохранить существующие тесты и добавить тесты на новые критичные состояния.
- Использовать текущий дизайн-стек проекта и MAX UI там, где он не ограничивает UX.
- Не добавлять тяжёлую библиотеку только ради одного компонента.

Минимальные тесты:

- создание обычного сигнала;
- создание регулярного сигнала;
- сохранение черновика;
- добавление места без потери формы;
- `EXACT`, `NEAR`, `UNVERIFIED`;
- ожидание минимального количества участников;
- пустой каталог;
- timeout и повтор запроса;
- защита от двойного submit;
- deep link на offer и plan;
- мобильная нижняя навигация;
- русская локализация дат.
- `UNVERIFIED` не отображается как обычный принимаемый Offer.

## Критерии готовности

Работа считается завершённой только если:

1. Новый пользователь без инструкции понимает смысл приложения по первому экрану.
2. Сигнал можно подать за 15–20 секунд.
3. Основной сценарий не требует читать длинные абзацы.
4. На каждом экране есть одно очевидное следующее действие.
5. Добавление места не уничтожает черновик.
6. При ожидании backend пользователь понимает, что происходит.
7. Каждый вариант отсутствия результата имеет понятную причину и действие.
8. Ни один переход не приводит к молчаливой потере данных.
9. Нет dev-текста, внутренних кодов и сырых ошибок.
10. Основной сценарий проверен вручную на мобильном размере.
11. TypeScript, lint, unit/component tests и production build проходят.
12. В конце агент предоставляет список изменённых файлов, результаты проверок, известные ограничения и необходимые backend-доработки.
13. Ни одна кнопка не ведёт на несуществующую функцию.
14. `UNVERIFIED` не превращён в обычный Offer.
15. Не добавлены новые внешние сервисы без явного согласования.

## Запрещено

- Не делать только косметический редизайн поверх старой структуры.
- Не добавлять больше текста вместо исправления непонятного сценария.
- Не создавать отдельный onboarding на 5 экранов.
- Не показывать пользователю технические причины и внутренние статусы.
- Не оставлять неработающие кнопки «на будущее».
- Не маскировать отсутствие данных красивой заглушкой без действия.
- Не менять смысл приватности ради более подробного объяснения совпадений.
- Не превращать `UNVERIFIED` в принимаемый вариант.
- Не подключать новый геокодер, карты, календарь или другую внешнюю интеграцию без согласования.
- Не завершать работу без ручной проверки полного основного сценария.

## Ожидаемый результат от агента

Агент должен самостоятельно внести изменения во frontend, адаптировать тесты и проверить результат.

Перед началом реализации он кратко фиксирует:
1. найденные API-ограничения;
2. какие состояния реально доступны frontend;
3. какие задуманные UX-элементы требуют backend-доработки;
4. план работ.

После реализации выдаёт:

1. что изменено;
2. какие сценарии проверены;
3. результаты lint/typecheck/tests/build;
4. какие изменения backend ещё нужны;
5. какие задуманные действия были сознательно не добавлены из-за отсутствия реальной поддержки;
6. скриншоты ключевых мобильных экранов.

Главный приоритет: **не красота сама по себе, а ощущение, что приложение невозможно использовать неправильно.**
