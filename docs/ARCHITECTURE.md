# Архитектура и жизненный цикл

Frontend обращается к product API; сервер скрывает таблицы и сообщает готовое состояние для текущего пользователя. MAX служит каналом аутентификации, уведомлений и deep link. Состояния домена и события outbox не зависят от формата MAX. PostgreSQL хранит компании, сигналы, кандидатов и ответы. Redis содержит только временный кеш запросов к KudaGo.

## Состояния

```text
Signal ONE_TIME (flow_version=2)
  -> Dvizh CHOOSING_CANDIDATES | NO_SOURCE | PROVIDER_UNAVAILABLE
  -> [личные WOULD_GO/PASS автора]
  -> явный launch -> COLLECTING_REACTIONS
  -> min WOULD_GO для одного seed -> AWAITING_CONFIRMATION
  -> min CONFIRMED -> GATHERED
```

До `GATHERED` возможны `CANCELLED`, `EXPIRED`, `NO_MATCH`; при отказе/истечении активного кандидата пересчёт выбирает запасного или возвращает в сбор реакций. Перед созданием сигнала проверяется пересечение с действующим подтверждённым движем — до provider I/O и записи раунда; после поиска проверка повторяется под блокировкой пользователя. Устаревший legacy Offer без действующего подтверждённого плана не блокирует новый сигнал. Перед запуском ещё раз проверяется актуальное число участников компании против `min_people`: ушедший участник не превращает запуск в заведомо несобираемый движ. Даже раунды `NO_SOURCE` и `PROVIDER_UNAVAILABLE` переходят в `EXPIRED` после дедлайна. Одноразовый Signal становится `FULFILLED` после сборки движа и `EXPIRED` после завершения без результата. `READY_TO_LAUNCH` выводится из `CHOOSING_CANDIDATES` + личного числа выбранных кандидатов. `WAITLISTED` — личное состояние подтверждения, не новый параллельный движ.

`dvizh_sessions`: один процесс на один сигнал и одну компанию. `dvizh_candidates`: ограниченный снимок реальных provider-объектов с временем, ценой и классификацией. `dvizh_reactions`: приватный soft-ответ пользователя, уникальный по candidate/user. `dvizh_confirmations`: отдельный окончательный ответ, также уникальный. `max_webhook_events`: отпечаток доставленного MAX Update. `outbox_notifications`: idempotent событие отправки через MAX adapter.

Чтение и действия проверяют членство компании. До запуска кандидат виден только автору, включая завершённый или отменённый до запуска раунд. Факт запуска определяется сохранёнными `seed`-вариантами. После запуска другим видны лишь выбранные кандидаты, собственный ответ и агрегатные числа. До `GATHERED` API не раскрывает список потенциальных участников; после показывает только реально подтвердивших.

Критические переходы блокируют строку `dvizh_sessions` через `FOR UPDATE`; уникальные ограничения и dedupe keys предотвращают двойной ответ, рассылку и повторный webhook. MAX callback и API-подтверждение содержат конкретный `candidate_id`, поэтому старая кнопка не подтверждает запасной вариант. Worker захватывает outbox через `SKIP LOCKED`, перед отправкой отсекает устаревшие Dvizh-уведомления, доставляет вне транзакции и повторяет сбои с backoff. Scheduler держит PostgreSQL advisory lock, создаёт регулярные раунды, проверяет истечение кандидатов, напоминания review/match, статусы неудачных и регулярных раундов, источник перед встречей и отдельное повторное подтверждение после сборки. Его изменения коммитятся отдельно от транзакции захвата lock. Вопрос перед встречей назначается по горизонту при сборке: за 24, 6 или 2 часа до начала, а при горизонте меньше трёх часов — сразу; неответившему приходит не более одного напоминания. Scheduler проверяет сроки уведомлений раз в минуту, `AUTOSIGNAL_POLL_SECONDS` задаёт частоту поиска регулярных сигналов. `withdraw` до начала пересчитывает состав и продвигает первого подходящего участника waitlist. Это обеспечивает единственное доменное действие; внешняя HTTP-доставка имеет обычную семантику at least once.

Нормализованный ответ провайдера содержит `source_fetched_at`; у старого снимка плана это время сохраняется, а в таблице `dvizh_candidates` отдельного столбца нет. Geoapify Places не предоставляет фотографии мест: для карточки backend получает карту с отметкой через Geoapify Static Maps, не раскрывая API-ключ браузеру.

## Источник и переход со старой модели

Реестр занятий (`leisure/taxonomy.py`) задаёт соответствие направления, занятия и категорий провайдеров. Для Dvizh KudaGo ищет временные события, Geoapify — обычные POI по категории и реальной границе города либо явно выбранному радиусу. Известный конфликт расписания, бюджета или расстояния отсекается; неизвестная цена даёт `UNVERIFIED` и остаётся в выдаче с честной подписью. `NEAR` допускает только ограниченное превышение с отдельным согласием. Итоговая выдача ранжируется и разбавляется по занятиям до существующего раунда из восьми карточек.

Перед запуском и финальным подтверждением API повторно проверяет ID и слот события либо признак закрытия места через KudaGo detail. Scheduler также перепроверяет источник собранного движа перед встречей. Подтверждённо исчезнувший вариант истекает, а ожидающие уведомления для него отменяются; после уже собранного движа подтверждённые участники получают сообщение об отмене источника. Временная ошибка KudaGo не трактуется как отмена. Адресный поиск Geoapify не замыкается на одном городе: локальные подсказки идут первыми, затем допускаются результаты других городов РФ; доступ к поиску и сохранение точки всё равно требуют компании соответствующего города.

Проверка живого [KudaGo API](https://docs.kudago.com/api/) 24.09.2026 подтвердила точные записи для боулинга, батутов и скалодромов в Санкт-Петербурге, верёвочных парков в Екатеринбурге и бань в Москве. Для них adapter читает `tags`, `title` и расписание с днями недели, включая работу после полуночи. Общий парк или отель, где занятие встречается только в описании, не считается точным кандидатом. `pc_club` и `thermal` пока скрыты из пользовательской таксономии: поиск KudaGo не дал достаточно надёжных площадок. Отсутствие подходящих записей в одном городе или временном окне означает только `NO_SOURCE` для этого запроса.

Миграция `20260924_0011_dvizh` сохраняет пользователей, компании, места и историю старых Offer/Plan. Неподтверждённые legacy сигналы, ожидающие приглашения и собираемые планы завершаются, чтобы старые уведомления не конкурировали с новым сценарием. Подтверждённые legacy записи остаются историческими. Старые API доступны только для чтения истории и для тестовой совместимости; создание legacy сигналов в production отвечает `410`. Legacy matching не получает новые сигналы, scheduler не возобновляет старые правила в production.
