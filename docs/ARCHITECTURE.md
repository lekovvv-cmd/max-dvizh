# Архитектура

Приложение — модульный монолит. API, обработчик уведомлений и планировщик используют один Python-образ и общую PostgreSQL; отдельного сервиса бота или брокера задач нет.

```text
MAX: бот ↔ Mini App (React / TypeScript / MAX UI)
                    │ HTTPS, initData
                    ▼
              FastAPI backend ──► KudaGo API
                    │                 ▲
                    ├── Redis: кеш запросов
                    ▼
                PostgreSQL
                 ▲       ▲
     scheduler ──┘       └── worker ──► MAX Bot API
```

## Где находится код

| Часть | Файлы и ответственность |
| --- | --- |
| Frontend | `frontend/src/features/`: Сигналы, Автосигналы, компании, приглашения и планы. `app/App.tsx` связывает экраны, `app/api.ts` задаёт типизированную границу API. |
| Стили | `frontend/src/styles/global.css` подключает токены, layout, карточки, формы, настройки Компании и диалоги, затем адаптивные и тематические правила. |
| HTTP | `backend/app/api/routes/product.py`, схемы в `api/schemas.py`. Проверки прав и оркестрация операций. |
| Авторизация | `backend/app/modules/auth/`: проверка MAX initData и пользователь. |
| Досуг | `backend/app/modules/leisure/provider.py`: KudaGo, нормализация и Redis. |
| Подбор | `backend/app/modules/matching/domain.py`: чистые функции совместимости, интервалов, Haversine и допустимого состава; `service.py`: транзакции и пересчёт. |
| Фоновые процессы | `matching/scheduler.py` проверяет Автосигналы; `max_integration/worker.py` отправляет outbox через `client.py`. |
| Хранение | `backend/app/db/models.py`; миграции Alembic в `backend/alembic/`. |

Frontend не обращается к провайдеру и не решает вопросы приватности или совместимости. Чистые функции подбора не зависят от HTTP, ORM и DTO KudaGo.

## Сущности и состояния

| Сущность | Назначение |
| --- | --- |
| User, Group, GroupMember | Личность MAX, Компания с городом/timezone, членство и роль. |
| Location | Личная GPS-точка, адресная подпись и признак точки по умолчанию в городе. |
| Intent | Условия Сигнала (`ONE_TIME`) или Автосигнала (`RECURRING`); несколько разовых строк могут иметь общий `signal_batch_id`. |
| CandidatePlan | Конкретный вариант с временем, пределами состава и состоянием сбора. |
| CandidatePlanSourceSnapshot | Единственный снимок фактов источника для варианта, включая происхождение и признак модели. |
| CandidatePlanMember | Приватная совместимость, личное расстояние и отклонения участника. |
| Offer | Личное приглашение с состоянием ответа и отметкой явного согласия на Near. |
| ConfirmedPlan | Подтверждённое состояние CandidatePlan, не отдельный каталог событий. |
| OutboxNotification | Уведомление, ключ дедупликации, попытки, время следующей попытки и аренда обработки. |

Основные переходы:

```text
Intent: ACTIVE → PAUSED / EXPIRED / CANCELLED; PAUSED → ACTIVE
CandidatePlan:
  COLLECTING → CONFIRMED_OPEN / EXPIRED / CANCELLED
  CONFIRMED_OPEN → CONFIRMED (вместимость или закрытие приёма)
  CONFIRMED_OPEN / CONFIRMED → COLLECTING
    при отмене до закрытия приёма, если допустимого состава больше нет
Offer:
  PENDING → WAITING_CONDITION / ACCEPTED / WAITLISTED
          / REJECTED / EXPIRED / INVALIDATED
  WAITING_CONDITION → ACCEPTED при выполнении личного условия
  ACCEPTED → WAITING_CONDITION при нарушении условия после пересчёта
  WAITLISTED → WAITING_CONDITION / ACCEPTED при освобождении места
  WAITING_CONDITION / ACCEPTED / WAITLISTED → CANCELLED_BY_USER
    до закрытия приёма
```

Состояния проверки источника у Intent: `NOT_CHECKED`, `PROVIDER_UNAVAILABLE`, `NO_SOURCE`, `NO_FEASIBLE_PLAN`, `OFFERS_READY`. Они различают ошибку провайдера и два вида пустого результата.

Уникальность обеспечивается для личности MAX, членства, пары план/пользователь в Offer, снимка плана и ключа outbox. Индексы покрывают владельца и состояние приглашений, компанию/состояние/время планов и активные условия. Полная структура — в моделях и миграциях, контракт ответов — в [OpenAPI](openapi.json).

## Транзакции и фоновые задачи

Принятие приглашения блокирует User → CandidatePlan → Offer и повторно проверяет состояние, время, условия и пересечения. Near требует подтверждения исключения. После записи ответа пересчитываются выбранный план и затронутые пересекающиеся варианты по сохранённым снимкам, без нового запроса к провайдеру. Уведомления записываются в outbox в рамках изменения данных.

Генерация блокирует Компанию, чтобы параллельные запросы и scheduler не создавали дубликаты. Создание и изменение пакета Сигналов получают данные провайдера до транзакции записи; условия, пересчёт и состояние провайдера фиксируются вместе. Ошибка откатывает изменения. Повторный refresh сверяет актуальность пакета и не создаёт дубликатов.

Scheduler по умолчанию проверяет семь дней каждые 30 минут. Время обработки вычитается из задержки до следующего запуска; если обработка дольше интервала, строгая периодичность не гарантируется. PostgreSQL advisory lock предотвращает одновременную обработку двумя экземплярами. После создания, изменения или возобновления Автосигнала API запускает фоновую проверку с отдельной сессией БД.

Worker захватывает строки через `FOR UPDATE SKIP LOCKED`, фиксирует `PROCESSING`, затем вызывает MAX вне блокировки. Ошибки повторяются с ограниченной задержкой, зависшие аренды возвращаются в обработку. Без токена процесс не отправляет сообщения. Дедупликация устраняет повторные логические задания, но сетевой сбой после отправки может привести к повторной доставке.

## Redis, данные и запуск

Redis хранит временные нормализованные выборки по городу, точному интервалу и категориям. При попадании в кеш запрос к KudaGo не выполняется; при промахе запрашивается только нужная выборка. PostgreSQL не служит запасным каталогом провайдера. Снимок сохраняется только вместе с конкретным CandidatePlan, имеющим хотя бы одного Exact/Near участника, и остаётся доступен после очистки Redis.

Compose запускает frontend (Nginx), backend, worker, scheduler, PostgreSQL и Redis. Backend применяет Alembic перед запуском API. Обновление существующей базы выполняется миграциями; удаление volume допустимо только для ненужных локальных данных. CI проверяет чистую установку и переход с заполненной ревизии `20260916_0005` на текущую `20260918_0010`, включая сохранение данных и заполнение категорий.
